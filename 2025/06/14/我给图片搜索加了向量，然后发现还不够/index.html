我给图片搜索加了向量，然后发现还不够

发表于 2025-06-14 分类于 AI 工程化

如果只记得一张图的内容，却忘了文件名，怎么把它找出来？PicIndex 就是为了回答这个问题。

我用多模态 Embedding 把图片和文字映射到同一个向量空间。搜“赛博朋克风格的雨夜街道”，或者“一只坐在窗边的猫”，系统会按画面语义把相近的图找出来。功能跑起来以后，问题一件接一件。图片里的订单号搜不准，大图调模型太慢，同一个查询还要一遍遍重新算向量。

换个更强的模型并没有解决这些事。PicIndex 后来的大部分改动，发生在模型之外。

搜得到雨夜街道，搜不到订单号

向量检索对模糊描述很友好。用户不用知道文件名，也不用记得某个标签，描述个大概，就有机会翻到想要的那张。这是我做 PicIndex 时最想要的效果。

图片里还经常有另一类信息。海报文案、合同上的人名、票据编号、产品型号。这些东西不模糊，越精确越好。模型能看出两张海报在讲同一个主题，碰上只差一位的编号，就不一定分得清。

于是我加上了 OCR，把一部分希望从向量上挪开。搜索时，向量那一路负责理解“这张图大概在说什么”，BM25 从识别出来的文字里找精确命中。“适合作为科技公司背景图”主要靠前者，“订单号 A20251014”要靠后者。

两条路都留着，模糊语义和精确文字各有入口。接着冒出来的问题是，两边都返回一堆结果，怎么把它们排进同一张列表。

两路结果都有了，排序更麻烦

先撞上的是尺子不一样。向量检索用余弦相似度，取值范围稳定；BM25 的分数没有上限，受词频、字段长度和命中方式影响。

直接把两个分数加起来，数值大的那一路会很自然地压过另一边。界面上写着混合检索，实际排序可能几乎由文本决定。

融合的办法我试过两种。现在默认用 RRF。它不比绝对分数，只看一张图片在两组结果里各自排第几。同一张图在两路都靠前，合并以后也靠前。这个方法不用先把两套分数调到同一个区间，手头没有标注数据的时候，它比调权重省事得多。

另一种是先归一化，再线性加权。

线性加权的好处是能按场景调。素材图看重视觉语义，就把向量的权重提高；票据和扫描件靠文字，就把 BM25 提高。麻烦在于没有离线评估集的时候，这些参数很容易变成“看起来还行”。所以 RRF 是默认值，只有场景足够明确，我才去动权重。

结果页上的“匹配度”另外处理过。Elasticsearch 的 _score 原样显示没有意义，我用分段映射把它换成百分比。这个数字只帮用户比较结果，不代表某张图有 92% 的概率符合查询。

耗时不一定花在推理上

最早调用多模态模型，我直接把 OSS 里的原图地址传过去。功能没问题，就是耗时不好看。手机照片几 MB 很常见，分辨率超过 4000 像素的也不少。模型内部会缩放，但原文件得先完整下载一遍。

一个直接的办法是让后端把图下载下来，压缩完再发给模型。这样做又多一段传输，CPU、内存和临时文件也都压到了应用服务器上。

最后用了 OSS 自带的动态图片处理。后端生成预签名地址时顺手加上缩放、质量压缩和格式转换的参数，原图还是只存一份，模型访问这个地址，OSS 返回处理过的图，应用服务器不参与压缩，也不用管临时文件。

我自己的测试数据里，发给模型的图片体积平均少了约 85%，Embedding 接口的端到端耗时降了 300ms 以上。收益会随原图大小、网络和模型服务变化。这次至少帮我确认了一件事，模型接口慢，时间不一定都花在推理上，文件大小和传输同样值得查。

入库流程也跟着改了。文件由前端直传 OSS，后端拿到 Object Key 之后异步跑 OCR、图片理解和 Embedding。上传请求不用等模型，服务器也不用中转文件流。

只缓存查询向量

每次搜索，查询文本都要先转成向量。“红色跑车”这种词反复出现时，模型做的是完全相同的计算，既拖慢等待时间，也增加调用成本。

缓存整个搜索结果很直观，但不适合 PicIndex。图片还在陆续入库，也会被删。缓存的是结果列表，就得想办法判断它什么时候失效，否则用户可能一直看到旧数据。

我只缓存查询文本对应的 Embedding。相同或者归一化之后相同的查询再来，直接从 Redis 取向量，照常去 Elasticsearch 搜。模型调用省掉了，结果仍然来自当前索引。

测试里，命中缓存之后取查询向量从约 500ms 降到约 20ms。严格说这不算语义缓存，缓存的只是那串文字算出来的结果。要让“红色汽车”和“红色跑车”共用一条缓存，还得单独维护查询向量索引，并且接受语义判断出错带来的误命中。这个复杂度对现在的 PicIndex 不划算。

向量之外，还缺筛选条件

语义召回解决的是“先把大致相关的图捞出来”。用户往往还想再收窄一点。搜完“周末露营”，可能只想看山地、白天、有帐篷、画面里没有人，或者只要横构图。

这些条件塞进向量相似度不合适，直接做成界面上的筛选项也排不出来。所以入库时多了一步，让视觉模型先抽出场景、风格、主体和时间这类结构化信息。

清洗过的标签以 keyword 字段存进 Elasticsearch，用户先用自然语言召回，再用这些字段过滤。有点像电商的分面搜索，区别是商品有现成的品牌、价格和类目，图片得先从画面里把这些东西提取出来。

到这一步，PicIndex 里的一张图不再只是一个向量。它同时带着 OCR 文本和一组可筛选的标签，向量管模糊语义，OCR 补精确文字，标签负责收窄范围。

后端还是 Spring Boot

这个项目从头到尾是 Spring Boot，我没有因为要调多模态模型就拆一套 Python 服务出来。PicIndex 不训练模型，Java 这边处理的是上传、权限、异步任务、Elasticsearch 检索、Redis 缓存和对外部模型服务的调用。

这些本来就在 Java 擅长的地方。要留心的是别把模型接口当成稳定的内部方法。它会慢，会限流，会超时，返回格式可能变，版本也可能换。PicIndex 把模型调用关在适配层里，给超时、重试、状态记录和降级留了位置。

放在应用层看，接 AI 服务和接支付、短信、第三方风控没有太大区别。模型决定能力上限，外围工程决定它能不能稳定地放进产品流程。这一块 Java 没有拖后腿。

还在验证什么

PicIndex 现在更像一次工程验证，离生产系统还有距离。混合检索的参数主要靠经验调，项目里没有足够的标注数据做离线评估。视觉模型抽出来的标签不一定稳，异步任务的重试和补偿也要继续补。数据量再往上走，索引构建和召回性能都得重测。

改一项值不值得留，我只看三件事。搜索有没有更准，系统有没有更好维护，多出来的复杂度有没有换来实际收益。现在这三条还答得上来，等数据量上去，答案大概要重算。
