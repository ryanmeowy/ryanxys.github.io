把 subagent 放回主循环

发表于 2026-11-01 分类于 AI 工程化

上个月，我把手上一个 agent 应用里的三个 specialist 删了。

倒不是为了省 token。主要是之前那套 orchestrator 加三个 subagent 的结构太折腾人：每加一个功能，我得同时改四个地方——路由的分类规则、subagent 自己的 prompt、主 agent 的 prompt，还有交接时的字段约定。

删完之后，跑了一遍回归测试。任务完成率没掉，端到端延迟差不多砍半。当然，这只是我自己粗看的结果，没做严格的 A/B。

刚好 10 月 22 号 Anthropic 的 Applied AI 团队发了一篇 Building agents: When to fold subagents into your main agent loop。看完挺有共鸣：原来大家都在往回退，而且他们拿严肃的测试数据把背后的账算清楚了。

传话游戏与有损压缩

Anthropic 这篇文章的核心就一句话：少拆点 subagent，把上下文和工具改成按需加载，不仅质量往往更好，成本和延迟也更低。（当然，这结论未必放之四海而皆准，有些地方我也不太买账。）

这其实挺反直觉的。最开始搭系统的时候，subagent 在我脑子里就是“解耦”的代名词：把复杂系统拆成职责单一的专家模块，各自管各自的 prompt、工具和归属，多干净。毕竟软件工程过去三十年一直都是这么教的。

但问题在于，传统软件工程的拆分，默认模块之间传的是精确的东西——函数签名、结构化数据、明确的接口契约。而 agent 之间传的是自然语言摘要。A 干完活总结一段话给 B，B 看着这段总结接着往下走。每一次交接都是一次有损压缩。到底丢了多少信息，你根本看不见。系统既不报错也不抛异常，只是最后出来的结果莫名其妙就变笨了一点。

Anthropic 把这叫“传话游戏”（telephone game），非常传神。第一个节点收到的是“用户反映最近两天订单状态没更新”，传到第三个 agent 耳朵里，可能就缩水成了“用户要查订单”——“最近两天”和“状态没更新”之间的因果关系，在路上全丢光了。

企业里是怎么长出一堆 subagent 的

既然有损，为什么企业里还是遍地 subagent？文章里剖析失败模式的那一段写得很透，因为它根本不是在聊技术，而是在聊组织架构。

假设大公司想搞一个统一的 agent 入口，把所有产品能力接进来。但每个能力归不同的团队管，最顺理成章的做法就是：各团队先各自封装一个 agent，平台团队在最上面搭个 orchestrator 把大家串起来。

这条路在汇报时最省事，但坑也是从第一天就埋下的。

首先是上下文在交接时不断丢细节；紧接着就是 subagent 泛滥，每个团队都发一个，最后攒出几百个功能重叠的模块，既没统一标准，边界也没人管。为了弥补上下文丢失的细节，各个团队开始使劲往 system prompt 里塞自家规则。塞着塞着，规则之间开始打架，连说话的语气都精分了——文章给这种怪物起了个名字，叫 Frankenprompt（缝合怪 prompt）。

评测（eval）也跟着散架。每个团队各自建一套针对自己子任务的测试集，拼命刷高自己那一亩三分地的分数，老板最后只能看着一堆注水的局部指标拍脑袋。更要命的是延迟：每多一层嵌套就多一次模型调用，这种物理耗时几乎没有优化空间。

文里给了一个真实案例的数据：一家客户把多 agent 框架拆掉、退回单循环之后，运行速度直接快了两倍。这跟我自己体感到的“延迟砍半”基本吻合。

说白了就是康威定律：agent 架构长成了公司组织架构图的样子。这话虽然不太中听，但我在好几个项目里都见过——系统切分的边界根本不是顺着上下文流向画的，而是照着汇报线画的。

为什么现在又能放回去了？

要不要拆 subagent，其实是个带时间戳的问题。

两年前真不行。那时候上下文窗口小，一个 agent 根本塞不下七八个领域的知识，硬塞进去就会注意力涣散、乱调工具。当年大家拆 subagent 是被逼无奈，真不是为了什么架构优雅，纯粹是窗口装不下。

现在之所以能退回单循环，文章列了三个变量。我基本认同，但这三条的份量不太一样。

第一，共享上下文确实能拔高上限。 跑长任务时，如果前几步的原始结果都原封不动地躺在同一个窗口里，模型自己就能把步骤 A 和步骤 C 的蛛丝马迹连起来。而在 subagent 模式下，主 agent 手里只有几份二手摘要，跨步骤联想的能力基本被废掉了。这点我在做 RAG 类应用时体会很深：把原始召回片段直接留在上下文里，模型经常能顺手捞出一些你根本没特地让它找的规律。

第二，渐进式披露（progressive disclosure）打破了容量瓶颈。 这是整篇文章最值得抄作业的地方。思路其实很朴素：agent 启动时只看得到一堆 skill 和 tool 的简短目录，真正用到哪一个，才把对应的完整指令加载进来。常驻内存的东西从“全套领域知识”变成了“领域知识的目录”，体积一下降了一两个数量级。

文章里有个数字我看完愣了一下：靠着把 skill 和 tool 改成按需加载，他们在较新模型上把 Claude Code 的 system prompt 砍掉了 80% 以上。

第三，也是我觉得最核心的一条：模型自己变强了。 从 Opus 4.5 开始，模型在单个循环里能扛住的复杂度，远超大多数工程团队的预期。现在的新模型懂得自己交代进度、自己回头验算结果，我们以前在代码里写死的那堆编排逻辑，现在看纯属帮倒忙。

这意味着外围框架（harness）的复杂度，应该随着模型能力的进化做减法，而不是做加法。文章里有句话点得很透：很多时候新模型发挥不出威力，恰恰是因为被老旧、僵化的多 agent 路由和交接协议把双手捆住了。

别矫枉过正，这三种情况还得拆

网上转发这篇文章时，标题大多起得挺耸动，很容易让人误以为“subagent 已经过时了”。但文章其实划了三条非常明确的红线——而且全是可测量的工程指标，不是主观审美：

  1. 单循环因为上下文膨胀，出现了可测量的性能下跌；
  2. 多个子任务需要并行处理，且跑完的过程上下文可以直接扔掉；
  3. 单个 agent 已经选不准工具，或者 system prompt 里的指令无法调和、互相打架。

文章说的“按上下文切分边界”：只有当某项工作几乎不需要跟系统其他部分打交道、最后只交回一个紧凑结果时，才值得拆出去。如果不符合这个条件，非要按问题类型拆、按部门拆，最后大概率又会变成传话游戏。

怎么安全地退回去？

文章给的改造路径很务实，没让人一上来就推倒重来。

第一步永远是先建 eval，这步逃不掉，哪怕先攒 10 条黄金用例（golden examples）也能起步。中央团队管端到端的大盘测试，业务团队给各自的 skill 备一套小测试。还在用 orchestrator 时重点看路由准确率（routing accuracy），放回主循环后，就改看有没有加载对 skill、有没有调对 tool。

具体动手时有三种改法，动静由小到大：

  • 合并（Merge）：最省事。看一眼线上流量，如果大量请求都是调完 A 紧接着必调 B，说明它俩本来就是紧耦合，直接捏成一个就行。
  • 当工具调（Subagent as a tool）：不动现有的 subagent，只是让主 agent 用 tool call 的方式去调它，话语权留在主 agent 手里。好处是零改动就能跑出个 baseline；坏处是老毛病全在——各自的 prompt 还得单独维护，每次调用依然伴随一次有损摘要和一层额外延迟。
  • 彻底放回（Fold in）：手术最大。把原本的 subagent prompt 拆成按需加载的 skill，把 API 暴露成基础 tool，一次挪一个，每挪一个就跑一遍前后对比。

在“彻底放回”这一步，文章提了一个极其隐蔽的坑，我读完印象特别深。

他们拿一个客服样例做放回测试时，发现延迟确实降了，总分也挺好看，但有一个原本百分百通过的老用例突然挂了。排查下来才发现：主 agent 手里本来就有订单查询工具，放回之后它变得“太聪明、太高效”了——自己查完订单状态就直接回复了用户，跳过了原本必须去问物流专家拿“预计送达日期”的那一步。

这种 bug 最要命。代码不崩，日志不报错，纯粹是因为 agent 效率变高、自己把活揽完了，结果漏掉了一句业务流程上卡死的必问项。如果你只盯着评测总分看，说不定总分还涨了两个点，代码直接就合进主干了。

更棘手的是，由于模型生成的不确定性，这个回归问题跑两次才复现一次。

所以他们的建议很硬：动手改造前，必须把线上常跑的调用链、以及业务上绝对不能破的红线规则全部写成测试用例，而且每个用例必须重复跑多次。想想我之前删那三个模块时，每个 case 只跑了一次就敢上线，纯粹是祖坟冒青烟。

真正的阻力不在代码，在领地

这篇指南表面上在探讨架构演进，但底子里的暗线其实是团队分工——而在真实公司里，改分工比改代码难十倍。

在旧模式下，每个业务团队交付的是一个完整的 agent。这个 agent 就是他们的交付物、他们的 KPI、他们的地盘。

如果按文章的建议改，业务团队以后交付的不再是 agent，而是零散的 skill 和 tool。中央留一个小团队，把控端到端质量和主 system prompt，所有新加的 skill、tool 和 eval 上线前都得过一遍中央的关；业务团队依然对自己的 skill 负责，也照样设 DRI 盯质量。

这套方案在技术上很合理，但在人性上很别扭。一个团队的产出，从“我们拥有一个独立 agent”变成了“我们往主循环里贡献了一段 Markdown 和几个函数”，听着就像被降级收编了。

Anthropic 显然也知道这事不好推，所以他们给出的解法是：拼命降低维护 skill 本身的门槛，甚至用 skill 来管理 skill。比如用 /skill-creator 自动起草和审计，用 /skill-doctor 监控每个 skill 到底消耗了多少 token、被触发了几次，顺手把没人用的僵尸 skill 清掉。至于这套工具能不能抚平业务团队的失落感，那就见仁见智了。

不过在工具设计这块，有两个实操经验非常值得直接抄：
一是工具数量上限。当工具定义超过 30 到 50 个时，模型选工具的准确率就会开始掉，所以最好按“用户意图”来聚合工具，别傻乎乎地一个后端 API 映射一个 tool。
二是把权限校验塞进 tool 内部。让每个 tool 自己去判断当前调用者能看什么、能改什么，越权了就直接返回一句自然语言报错给模型。这样一套单循环就能接待不同权限的角色。这个坑我们自己结结实实踩过——早期图省事，按用户角色硬拷了三份 agent，后来每次改点业务逻辑都得同步改三遍，苦不堪言。

我不太买账的几个地方

虽然整篇读下来很痛快，但有三个被文章轻描淡写带过的问题，落到实际工程里其实挺要命的。

第一，它默认你的任务大多是串行、且需要共享上下文的。
很多业务根本不是这样。如果你的场景天生就是要同时铺开十几条路——比如一次性扫描上百个代码文件、并行验证十个互不干扰的假设——那 subagent 的核心价值根本不是“做摘要”，而是换吞吐量。文章虽然用“research frontier”这种词顺嘴提了一句，但篇幅极短。我有点担心这会误导一批做高并发重任务的团队，盲目砍掉 subagent，等线上吞吐量崩了才反应过来。

第二，渐进式披露不是白捡的便宜，它的隐性成本出在“触发率”上。
把长 prompt 拆成按需加载的 skill 之后，模型能不能在正确的时机挑出那个 skill，全看那几句简短的 description 写得好不好。上下文是省下来了，但代价可能是模型压根没加载对技能。文章只说这“需要工程纪律”，但怎么评测一段描述能不能稳定触发，比调传统 prompt 玄学得多，目前也没有任何现成的指标可抄。我自己的土办法是：把 skill 的描述写成“什么时候该用我”（触发条件），而不是“我是什么”（功能介绍），这两者在实际触发率上差得非常远。

第三，也是门槛最高的一点：它把 eval 说得太轻巧了。
前面讲的所有架构红利，全建立在“你有一套靠谱的评测”之上。如果在内部系统耦合极深、没法轻易回放请求、也模拟不了真实用户行为的环境里，搭一套端到端的任务完成率评测有多难，做过的人都懂。文章给出的妙招是“记录关键事件的时间戳，事后做状态回放”——这招确实管用，但前提是你得先把全链路的埋点基建干完。

换句话说，想优雅地退回单循环，你得先具备精细度量现有系统的能力。而补齐度量能力的工程量，往往比删掉几个 subagent 大得多。我见过太多团队卡死在这里：架构演进的道理谁都懂，但手里拿不出一个能服众的评测数字，最后所有的技术重构都会沦为口水仗。

写在最后

整篇文章里，我觉得最值得贴在工位上的是结尾那段话：

As models evolve, our understanding of how to best use them and guidance around best practice evolve as well. That makes any one architecture less important than the principle behind it: measure, change one thing at a time, and keep what holds up.
（模型在进化，我们对最佳实践的理解也在变。这意味着任何具体的架构，都不如背后的原则重要：建立度量，一次只改一个变量，留下经得起验证的东西。）

要不要用 subagent 这个问题，过半年等下一代模型出来，说不定结论又会反转。

顺带提一句，他们这次还开源了一个配套的脚手架 anthropics/single-agent-loop-kit，把架构审计、跑 baseline、合并、放回、日常体检全串成了一个 Claude Code 的 skill，每走完一步都会停下来给你看结论、确认后再往下走。里面还带了个十分钟就能跑通的客服样例，设上 KIT_MODEL=fake 可以不花一分钱把整套流水线先试跑一遍。

不过就像那个仓库的 README 自己写的一样：如果你手头现在还没有历史遗留的 subagent，其实根本用不上这个工具——直接从头写一个单循环，省事得多。
