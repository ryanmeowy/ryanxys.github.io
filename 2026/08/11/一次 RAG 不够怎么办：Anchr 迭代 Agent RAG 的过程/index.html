一次 RAG 不够怎么办：Anchr 迭代 Agent RAG 的过程

发表于 2026-08-11 分类于 AI 工程化

Anchr 最早只有一条普通的 RAG 链路。用户提问，系统检索，重排候选，把排在前面的几个片段放进上下文，模型据此写出带引用的答案。

事实型问题走这条链路还行。比如问“文档重新解析后，旧索引怎么处理”，知识库里只要有对应说明，一次检索就能把材料捞上来，剩下的活是把它整理顺。

另一些问题的形状不一样。

找出几份设计文档里所有与任务恢复有关的内容，再比较进程重启、网络断开和主动取消三种情况下分别会发生什么。

这种问题很少有哪个现成片段能答完。第一轮搜索多半只找到 Agent 运行恢复的说明，读下去才知道后面还牵着异步任务（Task）。再去查 Task，又撞上进程内状态和持久化状态的区别。等翻到部署约束那一节，“恢复”这两个字的意思已经和第一次检索时不一样了。

下一步搜什么，得看上一段读到了什么。Anchr 的 Agent RAG 就是从这类问题上长出来的。

TopK 调得再大，也猜不到下一步要搜什么

固定 RAG 的检索发生在生成之前，一般只跑一次。材料不够时，最省事的办法是把 TopK 往大里调，10 调到 30，再调到 50，指望一次多捞一些。

这招对一种情况管用。相关内容本来就在首次召回的范围内，只是条数不够。任务恢复那类问题不在这里。用户的原话里未必出现“租约”“运行快照”“单实例”，第一轮检索没有理由替这些词留位置。

候选一多，没用的东西也跟着进来。一份长文档里相邻的段落常常一起命中，看上去拿回三十条，其中大半在重复同一件事。模型要在更多噪声里挑材料，却并没有多出新的查找方向。

我要的是两个分开的动作。先搜到入口，再读上下文。读到新线索，就再搜一次。

工具也照这个分成两个。搜索负责回答“东西在哪里”，顺序阅读负责补“这个位置前后还说了什么”。比如搜索已经命中这么一句。

新一代索引（generation）完成写入并通过可见性检查后，再把它设为当前生效版本。

这时候继续读前后段落，往往比再搜一次有用。上一段可能解释为什么不能直接覆盖，下一段可能说明旧版本什么时候清理。重新做一次全局语义检索，反而容易跳到另一处也提到索引版本的地方。

顺序阅读也有边界。整份长文档几百个片段，需要分批归纳再合并，这种事不该一直占着在线问答。它会被交给独立的后台任务。在线 Agent 只判断要不要转过去，不自己翻到底。

Tool Calling 很快能跑起来，规则却会越来越多

第一版主循环不复杂。模型拿到问题和工具说明，决定下一步是搜、是读，还是直接答。后端执行工具，把结果贴回上下文，再问它一轮。

跑通以后，问题很快从“能不能调工具”变成“几个判断撞在一起，听谁的”。

模型一次响应里可能带回好几个工具调用。立即并发执行的话，后面几个用的还是模型做决定时的旧上下文。第一个搜索要是已经翻出新线索，后面几个还值不值得跑，就说不准了。Anchr 把调用排进队列，一次只跑一个，每次动手前重新检查预算、重复调用和顺序阅读的限制。

串行之后还得防模型原地打转。现在的做法优先看 Tool Call ID，也就是模型给每次调用附带的那个唯一标识。没有 ID，就比工具名和参数。

语义相似度在这里不好用。模型两轮分别搜 agent recovery 和 how agent run recover，看着像重复，也可能是一次有效的改写。为了判断这件事再叫一次模型，费时间，费钱，结论还未必准。系统只拦可以确定的重复。模型换个说法反复搜，最后交给总预算收场。

去重只是其中一条规则。预算用完时队列里可能还压着调用，第一个工具失败后面几个可能已经没意义，模型给了答案后端一查引用还不合法。再加上用户点取消，这些规则很快会散在调模型、执行工具、提交最终状态的前后。

后来我把这块改成了显式状态机。理由很朴素，这次运行已经有了一套需要单独验证的执行顺序和收尾规则，散着写越来越难验。

状态机每次只回答三件事。现在在什么状态，刚发生了什么，下一步做什么。调模型、搜文档、读上下文这些有副作用的动作放在机器外面，跑完把结果当成一个新事件送回来。

拆开以后，“已经执行 8 次工具、手上有有效证据、队列里还剩一个搜索”这种局面可以直接摆成测试状态，看它下一步会不会收尾。测试不用真调八次模型，也不用赌模型刚好走进这条分支。分支一个没少，只是每个都能单独验。

下一步做什么有了答案，Agent 还得记住另一件事。这次运行里，它到底看过哪些材料。

模型“看过”哪些材料，由后端记账

Tool Calling 回来的东西是结构化参数，对后端来说仍然是外部输入，不能直接信。

用户这次只勾了“系统设计”和“Agent 设计”两份文档。模型某一轮生成了一个别的文档 ID。后端不能因为它是从 Tool Call 里带出来的就直接读。文档在不在、这个人有没有权限、是不是这次问答选定的范围，一条都不能省。

这些范围也会写进 Prompt，让模型少做无用功。权限不靠 Prompt 保。原先由浏览器传进来的参数，现在有一部分改由模型生成，输入校验、资源权限、文档版本过滤仍然留在服务端。

能读只是第一步。还要管最后能引用什么。

固定 RAG 一次只给模型一组上下文，引用从这组里挑就行。Agent 可能查好几轮。

到这里模型已经碰过八个片段。它的消息历史里还留着前几轮对话里的引用。最后答案只回一个编号，后端得知道这个编号指的是本次 Run 真读过的片段，还是历史引用、别的 Run 的证据，甚至是模型自己编出来的 ID。

每次工具返回片段，后端都往当前 Run 的证据集合里登记一笔。代码里管它叫 Evidence Registry。知识型回答只准引用这份账上的东西。

模型交卷以后，后端还要对一遍。回答类型和引用对不对得上，引用 ID 是否都在这份账上，正文里的引用标记合不合法。模型手上只有三个片段，答案里却引出第五个，这份答案过不去。

第一次没过，系统把具体错误送回模型，让它拿现有证据改一次。第二次还不行，这次运行就落到一个没有引用的安全结果上，不会为了修引用无限调模型。

这套校验只管引用来自这次查找，管不了模型有没有读懂原文。它完全可以引一段真材料，同时漏掉里面最要紧的限定条件。Citation 的作用是让人能点回原文核对。它不证明那句结论。

账本管住了最后能用哪些材料。还有一个问题悬着，这次执行最多能找多久。

到了上限就报错，会连已经找到的材料一起丢掉

固定 RAG 一次检索一次生成，Agent 却可能连着调好几轮模型和工具。不设上限，一次在线问答很容易变成一场不知道什么时候收的研究。

现在 Anchr 默认给 12 个模型步骤、8 次工具调用、90 秒总时长，单次模型调用最多 30 秒。预算不在开头查一次就算完，每次准备调模型或者跑工具之前，都要重新算一遍剩下的。

举个具体的。整个 Run 只给 90 秒，现在已经走了 84 秒。单次模型调用的常规超时是 30 秒，这一轮也不能再拿满 30 秒。不然 90 秒只是配置里写着的数字，实际执行还能在最后一次外部调用里超出一大截。

顺序阅读另外有配额。已经拿到证据以后，同一个 Run 最多真读两次连续的上下文。第三次还想往后翻，系统不再取正文，直接转去拿已有证据收尾。需要通读整份文档的问题，本来就该进后台总结任务，不该靠在线 Agent 一页页翻。

上限只回答了什么时候停。停下来时手上的材料怎么办，它没回答。Agent 已经搜了几轮、读了几轮，账上明明有能用的东西，只是模型还没来得及交卷。这时候把整次执行判成失败，前面的活就白干了。

预算耗尽以后，系统先看一眼账上有没有东西。

后一条路在代码里叫 Evidence Finalizer。它不把任何工具交给模型，也不许它重新规划查找路线，输入只有当前 Run 已经登记的证据。它收的是那种材料找到了、没能在预算内正常收尾的运行。本来就空的问题，它不会硬凑成一个完整答案。

这条路自己也会失手。剩余时间不够，或者模型仍然给不出合法的带证据答案，系统会把“有证据但收尾失败”这个降级结果留下来，不装成正常完成。没找到材料、找到了没答完、成功给出可验证的回答，是三种不同的结局。

有了这些上限，一次运行不会无限拖下去。但它仍然可能跑几十秒，页面和后端任务的关系就得重新摆。

问答变长以后，页面连接就不能代表任务本身

固定 RAG 很快。用户发完问题，等一下就出结果。Agent 要跑几十秒，中间搜好几次、读好几段、做几轮判断。页面只挂一个 loading，用户分不清它还在找，还是已经卡死了。

Anchr 用 SSE 把进度推到页面。当前是在决策、在搜文档，还是在读上下文，用户看得见。可以安全展示的回答也分段推过去，完整结果过了校验，再把页面上的最终内容校准一遍。

SSE 连接不等于 Agent Run。刷新页面、换网络、合上笔记本睡一觉，连接都可能断。断线就自动取消后端执行的话，用户只是刷了一下页面，前面查的几十秒也跟着没了。

现在的处理是，连接断了只停止往这个客户端推实时事件。后端照样跑完，把会话和 Run 状态存下来。用户回到页面，可以从已经落库的 Run、Task 或者会话消息里把结果找回来。Redis 里的运行快照用来辅助显示活动状态，MySQL 里的会话、Run、Step、Task 才是最终状态的依据。

在线 Run 和页面连接拆开之后，长文总结可以更彻底地下放。Agent 判断需要通读，就建一个后台任务，存好任务信息，当前请求直接结束。后台任务自己读全文、分批归纳、合并结果、更新进度。用户关掉页面，它也不靠原来那根 HTTP 连接活着。

断线不等于取消。用户真想中止，得另外发一次取消。这里冒出来一个跟 AI 关系不大的并发问题。Agent 答案生成完了，正准备提交完成，同一时刻用户点了取消。

只在流程里插几个布尔值检查不够用。最后一次检查和提交最终状态之间，永远留着一条缝。取消、完成、失败于是共用同一个临界区。取消先被接受，还没提交的完成或者失败就覆盖不了它。完成先落了地，迟到的取消也改不回来。

到这里，页面连接在不在、用户有没有点取消、后端最后提交了什么，成了三件要分开处理的事。Agent 为了多轮查找，确实多出不少运行成本和出错的地方。接下来的问题就很自然了，有了 Agent，原来那条固定 RAG 还留不留。

为什么最后还是保留了固定 RAG

从能力上看，Agent 能搜能读，自己决定什么时候答，覆盖固定 RAG 没有问题。可要问“这份文档哪年发布的”，一次检索就能撞上答案。走 Agent，至少先调一次模型决定去搜，搜完再调一次模型写回答。同一个问题多一轮调用，延迟和成本都上去了。

两条路就都留着。目标清楚、一次搜索大概能命中的，走固定 RAG。跨文档找、要连着读、得按中间结果改搜索方向的，由用户自己打开 Agent。这两类问题的分界线还没清楚到能交给自动路由，选择权先留在用户手里。

留着固定 RAG 还有个用处，当 Agent 的后路。固定 RAG 主要碰检索和生成失败。Agent 多出工具协议不合法、规划失败、工具边界异常、答案校验异常这些坑。配置允许的话，未预期的异常可以退回固定路径，重新走一遍路由、检索、生成。

这条后路救不回答案质量。本来就要多轮查找的问题，回到单次检索，多半只捞得回一部分材料。它只是在 Agent 编排自己出错时，让普通知识问答还能试一条更短、环节更少的路。两条路不等价。

现在这套 Agent 管得很窄。只碰 Anchr 里已经授权的文档，不联网，不执行代码，不开浏览器。一个问题从头到尾由同一套 Workflow 处理，没有再拆出 Research Agent、Reviewer Agent 之类的角色。它当下要做好的事还是那一件，一次检索不够时，沿着文档继续查下去，同时让知识范围、执行上限、引用来源都能被后端查。

把 Tool Calling 跑起来只是开头。固定 RAG 的步骤很少回头。Agent 让搜索、阅读、生成之间长出了前后依赖。系统于是要记住执行过什么、手上攥着哪些证据、还剩多少时间，最后是按完成收尾，还是走降级、取消。这些问题在 Tool Calling 的演示里基本看不到，却是 Anchr 从 RAG 走到 Agent RAG 时要补的主要部分。
