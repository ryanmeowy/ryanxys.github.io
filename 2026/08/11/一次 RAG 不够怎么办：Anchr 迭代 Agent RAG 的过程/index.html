一次 RAG 不够怎么办：Anchr 迭代 Agent RAG 的过程

发表于 2026-08-11 分类于 AI 工程化

Anchr 最开始只有一条传统的 RAG 链路：用户提问，系统搜出相关内容并重新排序，挑前几个片段塞给模型，最后生成带引用的回答。

应付大多数事实型问题，这条链路足够了。比如问“文档重新解析后，旧索引怎么处理”，只要知识库里有说明，搜一次基本就能拿到核心材料，剩下的就是让模型整理成通顺的话。

但有些问题没法这么干：

找出几份设计文档里所有与任务恢复有关的内容，再比较进程重启、网络断开和主动取消三种情况下分别会发生什么。

这种问题很难靠现成的几个片段拼出答案。第一次搜索可能只翻出 Agent 运行恢复的说明；顺着读下去，才发现还牵扯到异步任务（Task）；掉头去查 Task，又冒出进程内状态和持久化状态的区别。等最后去核对部署约束时，你对“恢复”这两个字的理解，早就和第一轮搜索时不一样了。

下一步搜什么，完全取决于上一步读到了什么。Anchr 的 Agent RAG 就是为了解决这种问题做出来的。

TopK 调得再大，也猜不到下一步要搜什么

传统 RAG 的检索都在生成之前，而且通常是一锤子买卖。材料不够怎么办？最直观的做法是把单次检索保留的候选数（TopK）从 10 调到 30 甚至 50，指望大力出奇迹，一次把东西捞全。

如果相关内容本来就在第一次召回的池子里，只是排名靠后，调大 TopK 确实管用。但前面的“任务恢复”问题不是这样。用户的原问题里压根没有“租约”、“运行快照”或“单实例”这些词，第一轮搜索怎么可能未卜先知，把它们的坑位留出来？

更糟的是，候选数放大后，垃圾信息也跟着进来了。一份长文档里挨着的几段话可能同时命中，看着拿到了 30 个结果，其实大半都在车轱辘话来回说。模型在一堆噪音里大海捞针，不仅累，还没法找到新的排查方向。

实际上我们需要把动作拆开：先用搜索找入口，再顺着读上下文；读出新线索了，就发起下一轮搜索。

所以我在 Agent 里给了两个不同的工具：搜索用来定位“东西在哪”，顺序阅读用来看清“这地方前后还聊了什么”。比如搜索命中了这么一句：

新一代索引（generation）完成写入并通过可见性检查后，再把它设为当前生效版本。

这时候最合理的动作往往是把它的上下段也调出来看看：上一段可能在讲为什么不能直接覆盖，下一段可能在讲旧版本什么时候清理。如果这时候不去翻上下文，而是再做一次全局语义搜索，很容易直接跳到文档里另一个八竿子打不着的“索引版本”章节去。

当然，顺序阅读得有个度。一篇长文档切下来可能有几百个片段，真要从头读到尾，得先分批归纳再合并，这种重活不适合卡着在线问答的请求干。遇到这种情况，应该转给独立的后台任务。在线 Agent 只负责判断要不要转后台，绝对不能自己没完没了地往下翻页。

Tool Calling 跑起来容易，但边界规则会越堆越多

第一版 Agent 的主循环非常简单：模型拿着用户问题和工具列表，自己决定下一步是搜、是读，还是直接回答。后端负责跑工具，把结果塞回上下文，再让模型做下一轮判断。

但循环一跑起来，问题马上就从“怎么调工具”变成了“一堆状况同时撞上怎么办”。

比如模型在一次响应里同时扔回来好几个工具调用。如果后端直接并发执行，那后面几个调用依赖的其实还是模型做决定时的旧上下文。万一第一个搜索已经摸到了新线索，后面几个原定的搜索还有没有必要跑，其实很难说。所以在 Anchr 里，工具调用会先排队，挨个串行执行。每次执行前，都要重新检查一遍预算、看看有没有重复调用、有没有超出阅读限制。

改成串行之后，还得防着模型犯傻、反复调同一个工具。现在的做法是优先看 Tool Call ID（模型给每次调用生成的唯一标识）；如果没有 ID，再去比对工具名和参数。

这里千万别用语义相似度去重。模型第一轮搜 agent recovery，第二轮搜 how agent run recover，字面意思差不多，但这很可能是一次有用的查询改写。如果为了去重再调一次模型来判断意思重不重复，既费钱又慢，还不一定准。所以系统只拦板上钉钉的完全重复。如果模型只是换着花样搜同一种东西，那就靠整体预算把它卡死。

去重只是冰山一角。工程上很快会遇到一堆破事：预算刚用完，队列里还排着两个工具没跑怎么办？第一个工具报错了，后面的还要不要继续？模型答案都写好了，后端校验却发现引用格式不对怎么处理？再算上用户随时可能点“取消”，这些控制逻辑很快就会散落在调模型、跑工具、提交状态的各个角落，糊成一团。

后来我干脆把这一块重构成了一个显式的状态机。倒不是说写 Agent 非得上状态机不可，而是当执行顺序和结束条件变得这么复杂时，你必须得有办法把它们单独拎出来验证。

状态机每次只认三件事：现在什么状态、刚发生了什么事件、下一步该干嘛。像调模型、搜文档这种有副作用的 IO 操作全剥离到状态机外面，跑完了再把结果包装成新事件喂回来。

这么一拆，写测试就舒服多了。想测“已经跑了 8 次工具、手里有可用证据、队列里还剩一个搜索没跑”这种刁钻场景，直接在内存里拼好当前状态喂给状态机，看它下一步是不是乖乖转去收尾就行。既不用真去调八次模型和搜索接口，也不用烧香拜佛指望模型刚好走出这条分支。状态机没法减少分支数量，但能让你把每个分支看清楚、测明白。

不过，状态机只管“下一步往哪走”，Agent 还有另一笔账要算：这趟跑下来，它到底看过了哪些材料？

模型“看过”什么，得由后端记账

Tool Calling 返回的虽然是结构化参数，但说到底还是模型生成的外部输入，后端绝对不能无条件信任。

打个比方，用户这次问答只勾选了《系统设计》和《Agent 设计》两份文档。结果模型在某一轮抽风，自己编了另一份文档的 ID 传过来。后端不能因为这是 Tool Call 传来的就直接去查库，必须老老实实校验文档存不存在、当前用户有没有权限看、在不在这次勾选的范围内。

虽然我们也会把文档范围写进 Prompt 提醒模型别乱来，但权限控制绝不能靠 Prompt 兜底。以前从前端传过来的参数怎么校验，现在模型生成的参数就得怎么校验，资源权限和版本过滤一步都不能省。

拦住了越权读取，接下来还要管住“嘴”——最后生成的答案到底能引用什么？

传统 RAG 只给模型喂一次上下文，引用肯定是从这堆材料里挑出来的。但 Agent 会经历多轮查找：

几轮下来，模型已经见过了八个片段，而且历史对话的上下文里可能还残留着之前几轮问答的引用编号。如果模型最后的答案里标了个 [3]，后端怎么知道这个 [3] 指的是这次真正读过的片段，还是之前聊天的残留记录，甚至是模型自己瞎编的 ID？

所以在 Anchr 里，每次工具返回文档片段，后端都会在当前 Run 的账本里记上一笔。代码里这叫 Evidence Registry（证据账本），专门记录“这次运行真正拿到过的文档片段”。最终生成的回答，只准从这本账里挑东西引用。

等模型交卷后，后端会对着账本做一轮硬性检查：回答类型和引用能不能对上？引用的 ID 在不在当前账本里？正文里的角标格式合不合法？如果账本里明明只有三个片段，模型却在答案里标了个第五个，这答案就会被直接打回。

第一次被打回时，系统会把具体的报错信息塞回给模型，让它就着现有的证据改一次。如果改完第二次还是过不了校验，系统就不会再跟它死磕了，直接降级返回安全的无证据结果，免得为了修几个角标把 Token 耗光。

当然，这套校验只能保证“引用确实来自这次查到的材料”，证明不了“模型真的读懂了原文”。模型完全可能引了一段真实的文档，却把里面的前提条件忘得一干二净。加引用角标只是为了方便用户点回去核对原文，不代表模型写出来的结论就一定是铁律。

账本建好了，引用管住了，但因为 Agent 可以自己决定继续搜、继续读，紧接着就会撞上下一个问题：这一趟到底允许它找多久？

到了上限就直接报错，前面的活就白干了

传统 RAG 是一锤子检索加一锤子生成，耗时很容易预估；但 Agent 可能会一轮接一轮地调模型、跑工具。如果不卡死上限，一次普通的在线提问很容易失控，跑成一个看不到头的后台调研。

目前 Anchr 的默认预算是：最多 12 个模型步骤、8 次工具调用、总耗时不超过 90 秒，单次调模型最多等 30 秒。而且这个预算不是在开头看一眼就完事了，每次准备调模型或跑工具前，系统都会重新抠一遍还剩多少额度。

举个例子，整个 Run 限时 90 秒，现在已经跑了 84 秒。哪怕单次模型调用的常规超时是 30 秒，这最后一轮也绝不能再给足 30 秒，最多只能给 6 秒。不然的话，90 秒的总限时就成了摆设，最后一次请求照样能把总时间拖长一大截。

顺序阅读也有单独的紧箍咒。在拿到有效证据之后，同一个 Run 里最多只允许连续翻页两次。当模型第三次试图继续往后读时，系统会强行打断，不再加载新正文，而是逼着它用已经拿到的材料开始收尾。要是某个问题真的非得把几万字的文档从头通读到尾，那它一开始就该走后台长任务，而不是在线上问答里没完没了地翻页。

不过，设上限只是解决了“什么时候踩刹车”，还有个更实际的问题：“踩死刹车的时候，手里已经找到的材料怎么处理？”

如果 Agent 已经兢兢业业搜了好几轮，账本（Evidence Registry）里也攒下了不少好材料，只差最后一步没来得及交卷。这时候如果因为超时或超步数，直接给前端甩一个“执行失败”，前面做完的有效功就全扔水里了。

所以在预算耗尽的那一刻，系统会先低头看一眼账本：

后面这条路在代码里叫 Evidence Finalizer。一旦进到这里，系统会把模型的工具全收走，也不准它再做什么新规划，输入里只有当前账本记下的片段。它的任务很明确：既然找过东西了，不管找没找全，先把手头的材料整理出来给个交代；当然，如果账本本来就是空的，也绝不硬编。

万一连这个收尾动作自己都失败了（比如剩下的几秒钟根本不够模型生成完，或者生成的引用还是不合法），系统就会老老实实返回一个“找到了部分材料，但未能生成最终回答”的降级状态，绝不硬装成正常完成。在 Anchr 里，“没找到材料”、“找到了材料但没写完回答”和“成功给出可验证的回答”，是三种完全不同的业务结果。

靠着预算控制和强行收尾，我们把单次运行时间按在了几十秒以内。但几十秒对前端页面来说已经很漫长了，浏览器连接和后端任务之间的关系也得跟着重新设计。

耗时变长后，就不能把任务绑死在页面连接上了

跑传统 RAG 只要几秒钟，用户提完问干等就行。但 Agent 动辄跑几十秒，中间要经历好几次搜索、阅读和思考。如果页面上只转一个冷冰冰的 Loading 圈，用户根本搞不清它是在认真查资料，还是早就卡死了。

为了解决这个问题，Anchr 用 SSE（Server-Sent Events）把后端的一举一动实时推给前端：现在是在做规划、在搜哪篇文档，还是在读哪段上下文，页面上一目了然。能提前展示的回答内容也会分段流式推过去，等最后整篇答案通过了引用校验，再把页面上的最终状态对齐。

但这里有个大坑：SSE 连接绝对不能等同于 Agent 任务本身。

用户随手刷个新、切一下 Wi-Fi，甚至合上笔记本电脑，都会导致连接断开。如果连接一断，后端就跟着把任务掐掉，那用户等了四十秒不小心按到刷新，心态直接就崩了。

现在的机制是，连接断了，后端只是不再往这个通道推实时事件，但 Agent 该怎么跑还怎么跑，跑完照样把会话和状态存进数据库。等用户重新打开页面，直接从落盘的记录里把结果捞出来就行。在架构上，Redis 里的运行快照只用来伺候前端的实时状态展示，真正说了算的最终状态，全在 MySQL 的会话、Run、Step 和 Task 表里。

把在线任务和页面连接解耦之后，前面提到的“长文档通读”也就顺理成章了。当 Agent 发现这活儿在线干不完，就会建一个独立的后台任务，把任务信息存好后直接结束当前的问答请求。后台任务自己在暗处慢慢读全文、分批总结、合并进度，用户就算直接关掉浏览器走人，也完全不影响它在后台跑完。

既然断网不等于取消，那用户真想喊停的时候，就得调专门的取消接口。这又引出了一个很经典的并发问题（跟 AI 倒是一点关系没有）：假设 Agent 刚好写完答案，正准备往数据库里写 COMPLETED；同一毫秒，用户嫌慢，伸手点了取消，请求打进来要写 CANCELLED。

如果只是在代码里随便找几个地方检查一下 isCancelled 布尔值，那在“最后一次检查通过”到“真正写入数据库”之间的这几毫秒窗口里，两边肯定会撞车。所以在实现上，取消、完成和失败这三个终态必须抢同一把锁（共用临界区）。谁先落袋，谁就生效：取消要是先写进去了，后面跑完的完成结果就得直接丢弃；反过来，如果答案已经提交成功了，晚一步到的取消请求也就不能再去篡改结果。

折腾到这一步，连接在不在、用户取没取消、后端到底算不算跑完，已经彻底拆成了三件独立的事。可以看出来，为了让 Agent 具备多轮查找的能力，系统背上了不少运行成本，也多出了很多可能翻车的环节。

这就逼着我们思考最后一个问题：既然 Agent 这么能干，原来的固定 RAG 是不是可以直接删掉了？

为什么最后还是留着固定 RAG？

从功能上看，Agent 会搜、会读、还会自己拿主意，确实能把固定 RAG 的活全干了。但算一下经济账就不一样了：假设用户只是问一句“这份文档的发布日期是哪天？”，固定 RAG 搜一次、生成一次就完事了；要是走 Agent，它至少得先调一次模型决定“我要去搜索”，等搜完拿到结果，再调一次模型写回答。同样一个简单问题，凭空多出一次模型调用，不仅慢，钱也花得冤枉。

所以在 Anchr 里，这两条路现在是并存的。目标很明确、搜一把就能出结果的简单问题，默认走固定 RAG；遇到需要跨文档比对、顺藤摸瓜往下读，或者得看一步走一步的复杂问题，再由用户手动打开 Agent 模式。因为这两类问题在实际场景里的边界还没清晰到能让程序百发百中地自动分流，目前还是把选择权交给了用户。

留着固定 RAG 还有另一个很实在的理由：拿它当备胎。

固定 RAG 会出错的地方无非就是检索和生成；但 Agent 链路长，幺蛾子也多：工具参数格式不对、规划死循环、工具执行异常、引用校验死活过不去……哪一步劈叉了都会导致任务失败。只要配置允许，一旦 Agent 在编排过程中遇到预期外的异常，系统就会自动退回到固定 RAG，老老实实走一遍单次检索加生成。

当然，这种兜底退路保不住复杂问题的回答质量。一个本来就需要翻三四次文档才能拼全的问题，退回到单次检索，大概率只能答出个片面结论。设置这个回退机制，只是为了在 Agent 框架自身抽风的时候，尽量给用户捞回一点东西，不至于直接报错开天窗，并不代表这两条链路可以画等号。

老实说，现在这套 Agent 的本事还很有限。它只能翻阅 Anchr 里授权过的文档，不能联网，不会跑代码，也没接浏览器操作。一个问题从头到尾就靠同一个 Workflow 串下来，没有搞什么 Research Agent、Reviewer Agent 互相开会的多智能体架构。它目前唯一想做踏实的，就是在单次检索不够用的时候，能顺着文档的脉络继续往下查；同时把权限边界、运行耗时和引用来源这几本账，在后端算得明明白白。

说到底，把模型的 Tool Calling 跑通只是万里长征第一步。传统的 RAG 是一条道走到黑，而 Agent 让搜索、阅读和生成互相咬合、前后依赖。为了兜住这种不确定性，后端系统必须自己长出记性：得记住跑过哪些工具、手里攒了哪些证据、兜里还剩多少时间，以及最后到底该按成功、降级还是取消来收场。

这些脏活累活很少会出现在演示 Tool Calling 的 Demo 里，但当你真想把 RAG 升级成生产可用的 Agent RAG 时，它们才是真正要啃下来的硬骨头。
