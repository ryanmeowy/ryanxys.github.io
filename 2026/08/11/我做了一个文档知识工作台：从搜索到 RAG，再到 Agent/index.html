我做了一个文档知识工作台：从搜索到 RAG，再到 Agent

发表于 2026-08-11 分类于 AI 工程化

最开始做 Anchr，我想解决的问题很具体：手里的文档越攒越多，怎么才能把里面的信息重新捞出来、真正用起来？

文件夹目录只能解决“文件存在哪”，系统自带的全文搜索又要求我必须记得原文用过哪些词。资料少的时候还能凑合；资料一多，常态就变成了：我明明记得某份文档聊过这事，但早忘了文件名，也想不起当时具体是怎么表述的。

所以 Anchr 是从文档搜索切入的。等搜索基本能用了，我才在检索结果之上接了生成回答；再往后，发现单次检索根本应付不了跨文档的复杂排查，这才顺理成章长出了 Agent。

虽然功能模块的名字一路从 Search 变成 RAG、再变成 Agent，但底下干的始终是同一件苦力活：把原始文档稳定地拆解成模型能用、用户又能随时跳回原文核对的证据。

这条链路有个很讨厌的特性：上游一旦丢了信息，下游怎么折腾都补不回来。

解析时把表格结构和页码搞丢了，后面搜索再准也没法还原现场；切分片段（Chunking）时把前置条件和结论一刀劈成两半，模型拿到的就只剩半截话；新旧版本的索引混在一起参与召回，重排模型再聪明也分不清哪份才是最新状态。做下来就会发现，RAG 里绝大多数答非所问，病根根本不在 Prompt 上。

技术文档尤其容易把这些毛病放大。一句工程结论往往同时卡着版本号、前置条件和运行环境：“默认开启”可能仅限某个大版本之后，“自动重试”可能只对幂等接口生效。上游只要漏掉一个限定词，模型就能拿着真实的原文片段，拼凑出一个看着滴水不漏、实则完全踩坑的回答。

先把文档拆成“带坐标”的片段

用户扔进来的是 PDF、Markdown、纯文本或者图片，但检索系统不能只存一个文件名加一大坨字符串。它至少得搞清楚哪些句子属于同一自然段、落在第几页、先后顺序是什么，以及插图和上下文之间是怎么对应的。

在 Anchr 里，所有入库文档都会先交给独立部署的 Python sidecar 服务（anchr-docling）做解析。主服务只管异步提交任务、轮询状态，最后收回结构化的数据。

把解析入口收拢之后，后面的链路就彻底不用关心“PDF 的第三页”和“Markdown 的第二个二级标题”有什么格式差异了。下游眼里只有统一抽象出来的文本块、图片、页码、标题层级和坐标。不同文件格式的脏活在解析层被消化掉，而用来回溯原文的位置结构则一路保留到底。

这套机制对 PDF 尤其关键。Markdown 和纯文本天生带着阅读顺序，而 PDF 本质上是一张排版画布，文字、表格和配图全靠页面坐标拼出语义。假设一份分布式事务协议文档用表格列出了“执行阶段、参与者状态、持久化记录、故障恢复动作”，如果粗暴地按 PDF 内部的字节流顺序硬抽文字，prepared 状态的恢复动作极有可能和 committed 状态串行拼到一块。借用 Docling 恢复表格和版面结构、同时记下页码与坐标，是整条链路不歪的第一步。

解析出来的文档不会整篇塞进一条索引，而是继续切分成一组 Segment。它是 Anchr 搜索和引用的最小单元：普通段落、图片 OCR 出来的文字、乃至文档里的原图，都是独立的 Segment，各自带着所属文档、页码、序号和坐标。需要做语义检索的内容，再过一遍 Embedding 转成向量。

这里我没有把所有模态强行拍扁成同一种纯文本：

  • 普通段落直接拿正文算文本向量；
  • OCR 出来的文字参与全文检索；
  • 如果配置的 Embedding 模型支持多模态，原始图片还会保留独立的视觉向量。

比如文档里有一张“协调者故障恢复”的时序图，它既可能因为图里的 prepare、commit 字样被全文检索捞出来，也可能因为整体的交互拓扑结构被多模态向量命中。不管走哪条路，最后都会落回同一份原始文档的同一个坐标上。

怎么切分 Segment 也不是光调一个 chunk_size 就能搞定的。切得太碎，“参与者进入 prepared 状态后必须保留锁和事务日志”跟后半句“直到收到最终决定或完成故障恢复”分家了，前一半就成了没有终止条件的死规矩；切得太粗，一个片段里又把正常提交、协调者恢复、启发式处理全揉在一块，不管是算 BM25 还是算向量相似度，焦点都会糊掉。

我的解法是把“搜索定位”和“上下文阅读”拆成两件事。检索时用颗粒度偏小的 Segment 做精准打点；等用户点开原文预览、或者需要给后续步骤补充上下文时，再顺着序号把前后相邻的片段一块捞出来。这比直接把检索块切大灵活得多，也让搜索、引用和原文预览直接复用了同一套位置坐标。

新索引没写完，旧内容先别动

文档解析、调 Embedding 接口、写 Elasticsearch 索引，全是有外部依赖的慢操作，耗时很不稳定。如果前端上传请求一直同步干等着整条链路跑完，碰上一份大体积 PDF 或者 Embedding 接口限流，连接直接就挂死了。所以在 Anchr 里，入库全是后台异步任务——上传成功只代表文件落了盘，不代表马上就能搜到。

同一个上传批次里，每份文档都有自己独立的状态机，顺着“解析 -> Embedding -> 写索引”往前推。单份文档挂了不会拖死同批次的其他文件，前端页面上的进度条也能直接映射到真实的阶段。

把阶段拆开后，报错也就不再是一句黑盒的“入库失败”：到底是 Docling 没拉到源文件、解析出了空内容、Embedding 触发了限流，还是 ES 写入超时，位置一清二楚。针对 Docling 和 Embedding 的偶发抖动，进程内会做有限次数的自动重试；实在过不去的，就把失败阶段和原因记下来，留给用户在界面上手动重跑。

新文档第一次入库，无非就是等流水线跑完。但一旦系统支持“重新解析、重建索引”，马上就会撞上一个更棘手的并发问题：旧内容在哪一秒下线？新内容又从哪一秒开始对搜索可见？

设想一份部署手册把运行环境要求从 JDK 17 改成了 JDK 21。重建索引时，如果先删旧数据再写新数据，在构建窗口期内这份手册就等于人间蒸发了；如果边写边覆盖，用户同一次搜索里就可能同时搜出“必须用 JDK 17”和“必须用 JDK 21”。对检索系统来说，最怕的不是磁盘上暂时存了两份数据，而是新旧两个版本在同一次查询里同时露面。

为了解决这个切换问题，Anchr 给每次构建任务发了一个递增的索引版本号（generation）：

  1. 重建期间，老版本继续正常对外扛搜索流量，新版本在后台静默跑完解析、向量化和 ES 写入。
  2. 等 ES 写完，主服务不会光看“最后一次请求没报错”就立刻切流，而是去核对实际写入的文档 ID、目标版本号，以及应写的 Segment 数量是否完全对得上。
  3. 真正落锤切换前，还会再去查一眼文档的当前状态——万一构建中途用户把文档删了，或者又触发了一次更新的构建任务，这次慢吞吞跑完的任务就会直接作废，绝不会把已经删掉或过期的旧数据“诈尸”写回来。

这套方案并没有去搞 MySQL 和 Elasticsearch 的分布式事务。MySQL 是唯一认定的真相源（记录当前生效的 generation），而 ES 只是随时可以重建的搜索副本。 检索时，ES 可能会把多个历史版本的候选块一起召回来，但主服务会拿着 MySQL 里的当前生效版本号做一次硬过滤，对不上号的直接扔掉。

至于老版本的数据、以及半路夭折的构建残骸，全交给后台异步清理任务慢慢扫。哪怕清理任务一时半会儿挂了，或者 ES 里多躺了几个未激活的幽灵版本，用户在前端看到的内容也丝毫不受影响——什么时候翻篇，全听 MySQL 里的版本号指挥。

一次搜索，既要盯死“原词”也要兜住“大意”

在真正去索引里捞数据之前，第一步是先把搜索边界锁死。用户到底是在整个知识库里大海捞针，还是已经点进了某本特定的技术手册里提问？这个范围必须最先敲定。后面的查询改写只能优化“拿什么词去搜”，绝不能偷偷扩大圈定的文档范围，否则当前上下文之外的野资料就会混进答案里。

锁死范围之后，再去处理用户的提问本身。人在连续对话时是很省字数的——比如先问了一句“PostgreSQL 的 Serializable 隔离级别为什么还会让事务失败？”，紧接着追问一句“那只读事务也会吗？”。如果直接拿后半句去搜，数据库类型、隔离级别、序列化冲突这几个核心前提全丢了。所以 Anchr 会带上最近几轮对话把问题改写补全；万一改写模型超时或者吐出乱码，就直接降级回用户的原始提问继续搜。改写只是帮召回打辅助，不会覆盖掉用户原本的问题。

接下来就是多路召回。全文检索和向量检索各有各的死穴：

  • 用户问“为什么数据库为了保证可串行化反而会主动回滚事务”，手册里的原话可能是“检测到可能产生不可串行化结果的读写依赖，需中止其中一个事务”。字面几乎没重合，但聊的是同一个并发控制机制——这得靠向量检索去兜。
  • 反过来，像 SQLSTATE 40001、类名、配置项，或者 could not serialize access due to read/write dependencies 这种报错原话，一旦被化成了模糊的语义向量，准头反而暴跌——这必须靠全文检索死磕字面。
  • 如果配了多模态 Embedding，同一个查询向量还会顺道去捞文档里的架构图和时序图。

这三路召回打出来的原始分数根本不在一个量纲上，直接加权求和，分值跨度大的那一路肯定霸榜。所以 Anchr 用了 RRF（倒数排名融合），不看绝对分数，只看候选块在各自榜单里的名次。一个 Segment 如果既踩中了报错码原词、语义向量又排在前列，名次就会往上蹿；只在单路露脸的结果，也不会因为分值体系不同被直接拍死。

RRF 融合完之后，先做当前版本过滤，再做结果打散，最后才送进 Rerank（重排模型）。

这个先后顺序非常关键：旧版本的过期片段哪怕字面再匹配，也不该占着茅坑，更不配消耗宝贵的 Rerank 算力；如果把版本过滤放到最后一步，过期数据在前面就把名额占满了，真正的新版内容反而进不了重排。

同样，“打散（多样化）”放哪一步也有讲究。一份长文档里相邻的几段话很容易同时命中，如果不加限制，Top 10 里可能八条都来自同一篇长文。所以在搜整个知识库时，Anchr 会在 Rerank 之前限制单篇文档、单一类型的入选上限，把窗口留给更多资料；但如果用户本来就指定了只在单篇文档内提问，目标就变成了“把这篇文档里最相关的段落全找出来”，这时候打散动作就会推迟到 Rerank 之后，免得在重排前误杀了连续的关键上下文。

说到底，Rerank 只是在已经收窄的候选池里做精排，它不是第二轮召回。前面被范围、版本号或名额上限卡掉的内容，Rerank 是变不出来的。最终排序会把归一化后的检索分与 Rerank 分结合起来看；万一 Rerank 服务抽风或超时，系统就直接回退到 RRF 的排序结果，保证主链路不断。

搜出来的候选，不能一股脑全塞给模型

搜索列表页和回答生成模型，对检索结果的要求其实是拧着的。

人看搜索列表时，习惯先扫一眼几张文档卡片，挑感兴趣的点进去细看；而生成模型的上下文窗口寸土寸金，多塞一个无关片段，不仅烧 Token，还会拉高模型张冠李戴、把 A 文档的条件嫁接到 B 文档结论上的概率。

所以在展示层，Anchr 会先把排好序的 Segment 按所属文档聚合成卡片，每张卡片挑出排名最靠前的命中片段。用户看到的是“哪几篇资料值得点开”，而不是满屏来自同一个文件的碎片。

而喂给固定 RAG 生成模型的证据，则会在这个基础上做二次收缩：最多只挑 5 个有真实 Segment ID、能对上前端卡片、且包含实质文本的片段。 宁可少给，也绝不把 Top K 原始结果全倒进 Prompt——否则重复段落、边缘废话和不同版本的冲突说明混在一起，模型在组织语言前还得先替检索系统干一遍去噪的活。

这里对图片召回也划了一条硬边界：纯视觉向量帮你捞出了一张高度相关的架构图，但如果这张图周围没有任何可供引用的文字说明，它就只能呆在搜索结果卡片里供人查阅，绝不会直接塞给模型当做生成结论的依据。能帮上排序的忙，不等于就能当呈堂证供。

真正组装生成 Prompt 时，里面会分门别类塞进四样东西：用户的原始提问、检索用的改写查询、当前回答模式，以及带编号的证据列表。之所以把“原始提问”和“改写查询”同时亮给模型，就是为了防一手——别让“为了扩大召回面而补写的检索词”反客为主，带偏了用户真正想问的问题。

在按下模型调用的扳机前，后端还会卡一道前置体检：如果手里连一个可引用的 Segment 都没有、或者有效文本短得可怜、又或者检索得分全面偏低，系统会直接短路返回“证据不足”，压根不去调生成模型。这样既省了钱，也避免了让模型在极其单薄的上下文上强行脑补，同时把“资料库里确实没这方面证据”和“大模型接口挂了”清清楚楚地区分开。

模型写完了，后端还要拿代码验货

生成模型被要求必须返回带状态码和引用编号的结构化数据：证据够就返回 ANSWERED，不够就返回 NO_EVIDENCE。

哪怕模型老老实实返回了 ANSWERED，这份回答在后端眼里也只是个“待审草稿”。用过模型的都知道，它随时可能吐出格式残缺的 JSON、顺手捏造一个根本不存在的引用编号，或者洋洋洒洒写了一堆硬核结论却一个角标都不打。这种毛病靠在 Prompt 里写一百遍“请勿编造”是治不本的，必须用代码做硬校验。

Anchr 的后端会严格解析返回结构：核对状态码、检查正文中出现的引用角标是不是都在输入的证据编号范围内（比如只喂了 1 到 5 号证据，正文里却蹦出个 [7]，直接打回），并确认知识型结论是不是真的挂上了引用。

校验过关后，后端会做一次清洗：**只保留正文里真正引用到的 Segment**，绝不把没用上的陪跑候选一股脑包装成“参考资料”充数。留下的片段再按文档合并、重排角标，把文件名、页码、原文坐标和命中原因补齐。如果模型自己没写出像样的引用说明，系统就直接拿检索阶段生成的匹配摘要顶上，不去为了凑句漂亮话再调一次模型。到这里，最开始解析阶段苦苦保留下来的坐标信息，才真正变成了前端页面上一点就能跳过去的原文高亮。

前端流式输出时也有个细节。模型吐给后端的 JSON 里夹着状态码、引用列表等协议字段，这些不能原样漏给用户看。服务端在流式推送时，只会从增量字符流里剥离出正文部分往前端推；等整段生成彻底结束、跑完上述的后置校验后，如果发现校准后的最终文本跟刚才流式推过去的内容有出入，前端会用校验通过的定稿做一次静默替换。流式输出是为了消掉干等的焦虑，而最后的硬校验才决定这轮回答算不算数。

最后，这轮生成的回答、角标、结果卡片，连同底下走过的完整检索轨迹（改写成了什么、哪路召回的、过滤掉了谁），都会跟着会话一起落库。用户刷新页面不会丢现场；哪天发现某个问题答得不对劲，我也能顺着存下来的轨迹一路倒查：到底是查询改写歪了、召回漏了，还是被版本过滤、Rerank 或者后置校验给误杀了。如果只存最后那段聊天记录，整条 RAG 链路出了问题就是一个死无对证的黑盒。

当然，角标只能证明“模型写这段话时参考了哪一页”，没法保证模型一定读懂了原文。比如 PostgreSQL 文档里明明写的是“VACUUM 无法清理仍可能被活跃事务快照看到的旧行版本”，模型总结时还是可能顺嘴滑成“长事务会完全阻塞 VACUUM 运行”——把“部分旧版本无法回收”夸大成了“整个清理进程卡死”。

引用机制消灭不了这种阅读理解偏差，但它至少给用户留了一扇立刻跳回原文对质的门。到这一步，单次检索的固定 RAG 链路才算真正闭环。

固定 RAG 的欠债，与 Agent 的起点

目前这套固定链路，已经能把静态文档洗成带坐标的证据，走完“多路召回 -> 融合重排 -> 证据准入 -> 生成与引用校验”的全流程。但工程上还有几笔明确的欠债要还：

  • 入库任务如果碰上主服务重启，目前还不支持从中间阶段断点续跑；
  • 检索链路虽然搭齐了多路召回、RRF 和 Rerank，但手里还缺一套成规模的人工标注测试集来做离线打分；
  • 回答生成失败与证据不足的边界判定，还可以抠得更细。

不过，这些都属于单次检索链路内部的修修补补。真正让我决定继续往下写 Agent 的，是另一类靠“把单次检索调准”根本无解的问题。

这篇文章聊的固定 RAG，在开口回答前只有一次检索机会。如果你问“PostgreSQL 的普通 VACUUM 为什么通常不会缩小磁盘上的表文件”，只要这一枪搜到了“内部空间复用”和“操作系统文件截断”的区别，固定链路就绰绰有余了。

但要是问“PostgreSQL 只读副本的复制延迟为什么一直在涨”呢？这背后可能卡在主库 WAL 发送、网络传输、备库接收落盘，也可能是备库回放跟长查询撞出了锁冲突，甚至还得去翻当前的配置参数。你必须先搜第一枪，看清延迟到底卡在哪个环节，才能决定下一枪是去查网络吞吐还是去查回放冲突。当下一步搜什么完全取决于上一步读到了什么时，单次检索的固定 RAG 就撞墙了。

Anchr 的 Agent 就是从这面墙开始往后写的。它没有另起炉灶搞一套新检索，而是直接复用了上面讲的整套召回、版本过滤和引用校验底座，只是把“单次调用”放进了一个允许模型看中间结果、自己决定怎么追查的循环里。

至于把这个循环放开之后，怎么管住它的调用预算、状态流转和证据边界，留到下一篇《一次 RAG 不够怎么办：Anchr 迭代 Agent RAG 的过程》再细聊。
