我做了一个文档知识工作台：从搜索到 RAG，再到 Agent

发表于 2026-08-11 分类于 AI 工程化

最开始做 Anchr，我想解决的问题很具体。手里的文档越来越多，怎么才能把里面的信息重新找出来、用起来？

目录解决的是文件放在哪里。系统自带的全文搜索要求我还记得原文用过哪些词。资料少的时候，这两种办法都够用。资料一多，更常见的情况是我记得某份文档讲过这件事，却忘了文件名，也不记得当时那句话是怎么说的。

Anchr 就从文档搜索做起。搜索能用了，我才在检索结果上生成回答。再往后，一次检索处理不了跨文档的问题，才有了 Agent。功能名字从 Search 换成 RAG，又换成 Agent，底下做的还是同一件事，让原始资源稳定地变成模型可以用、用户又能回到原文核对的证据。

这条流程有个很别扭的地方。前一步丢掉的信息，后一步基本补不回来。

解析时丢了表格和页码，后面搜得再准，也还原不出那句话在原文里的位置。分段把条件和结论切开，模型拿到的就是半句话。新旧版本一起参与召回，重排分不清哪一份才是当前生效的内容。RAG 里不少问题出在 Prompt 之外。

技术文档最容易暴露这些。一个结论往往同时被版本、前置条件和运行环境限定住，“默认开启”可能只对某个大版本成立，“会自动重试”可能只针对幂等请求。上游漏掉一个限定，模型完全能拿真实原文拼出一个讲得通、却少了条件的回答。

先让文档变成可以定位的内容

用户看到的是 PDF、Markdown、纯文本，或者一张截图。检索系统要的不是文件名加一大段字符串。它得知道哪些内容属于同一段，这段话在第几页，前后顺序怎么样，图和文字之间有没有关系。

Anchr 里，进入入库任务的资源都交给 Anchr Docling 解析。它是一个单独跑的 Python sidecar，放在主服务旁边专门处理文档。主服务负责提交任务、跟踪状态，再接收它返回的结构化结果。

解析入口统一以后，后面的环节不用再分别理解“PDF 第三页”和“Markdown 第二个二级标题”。它拿到的是文本块、图片、页码、标题和位置。文件格式的差异在解析阶段被吸收，用来回溯原文的那部分结构必须留下。

PDF 最吃这一套。Markdown 和纯文本天生有阅读顺序，PDF 更像一张排好的画布，文字、表格和图片要靠页面位置才能组成语义。假设一份分布式事务协议说明用表格列出执行阶段、参与者状态、持久化记录和故障恢复动作，只按 PDF 内部的存储顺序抽字，prepared 状态的恢复动作很可能跟 committed 拼到一起。Docling 会尽量把这些结构恢复出来，页码和页面位置也一并保留。

解析后的文档不会整份写成一条搜索数据，而是继续拆成一组 Segment。Segment 是搜索和引用用的基本片段。文本段落、从图片里识别出的文字（OCR）、文档里的图片，都可以成为独立的检索单元，各自带着文档、页码、顺序和位置。需要语义检索的内容会再过一次 Embedding，转成能比较的向量。

这里没有把所有内容压成同一种文本。普通段落用正文生成文本向量，OCR 出来的文字可以参与文字检索。Embedding 配置支持多模态时，原始图片还能留一份独立的视觉表示。一张画着协调者故障恢复的时序图，可能因为图里的 prepare、commit 被全文检索命中，也可能因为整体交互结构被向量检索找到。两条路最后都要落回同一份原始资源的具体位置。

分段也不是调一个长度参数就完事。切得太小，“参与者进入 prepared 状态后必须保留锁和事务日志”和“直到收到最终决定或完成故障恢复”会落到两个片段里，前一句就丢了终止条件。切得太大，一个片段又混进正常提交、协调者恢复和启发式处理几条路径，全文相关性和向量表示都跟着糊掉。

最后我把“搜索命中哪一段”和“用户需要读多少内容”拆成了两个问题。搜索先用小 Segment 定位。人打开原文，或者后面要更多证据时，再顺着顺序取回相邻片段。这比直接放大检索片段灵活，搜索、引用和原文预览还能共用同一套位置信息。

文档到这儿已经变成有结构、有位置的片段，下一步是写进索引。麻烦在于写入不是一次就能完成的操作。新内容写到一半时能不能被搜到，成了紧接着要处理的事。

新索引没写完，旧内容先别动

文档解析、Embedding 和索引写入都要访问别的服务，耗时很不稳定。上传请求要是等到整条流程跑完，一份复杂 PDF 或者一次 Embedding 限流就能长时间占着连接。所以 Anchr 把入库做成了后台任务。上传成功只说明原始资源交给了系统，不说明它马上能搜。

一个批次里，每份资源有自己的处理项，状态随着解析、Embedding 和写索引往前推。某份文档失败，已经成功的文档不会被一起拖住。页面上的进度也对得上真实的处理阶段。

阶段分开以后，失败不再只是一句笼统的“入库失败”。Docling 没取回原文件、解析结果为空、Embedding 服务限流、Elasticsearch 没写进去，这些事发生的位置不同，后续处理也不一样。Anchr 会在进程内对部分短暂的 Docling 和 Embedding 错误做有上限的重试。处理项最终失败，就留下失败阶段和原因，用户可以整份重新处理。

新文档第一次入库，只要等这条流程跑完。允许重新解析和重新向量化之后，多出一个更难的问题。旧内容什么时候不再可见，新内容又从哪一刻开始参与搜索？

假设某份部署手册把运行时要求从 JDK 17 改到 JDK 21。重新处理时先删旧索引，新版本建好之前，这份手册会从搜索里消失一阵。新旧 Segment 边写边覆盖，用户又可能同时搜到“JDK 17”和“JDK 21”。索引里暂时躺着一份没激活的数据，用户看不见。麻烦的地方是同一次查询里新旧两份同时可见。

Anchr 会给每次内容处理分配一个独立的索引版本 generation。旧版本继续提供搜索，新版本在后台完成解析、向量化和索引写入。只有写入数量和目标版本都通过检查，新版本才激活。旧版本和激活失败的新数据，交给后台慢慢清理。

激活不能只看最后一次 Elasticsearch 请求有没有报错。写入完成后，主服务要核对写入结果是不是属于当前文档和目标版本，可读的 Segment 是不是都写全了。切换之前还得再看一眼文档状态。文档在这期间被删除，或者这次处理已经被更新的版本超过，它就不会激活。这道检查挡住的是那种跑得很慢的后台任务，结束时把已删除、已更新的文档又写回来。

这里没让 MySQL 和 Elasticsearch 进同一个分布式事务。MySQL 记录当前生效的版本，Elasticsearch 存一份可以重建的 Segment 搜索副本。查询可能从 Elasticsearch 拿到多个版本的候选，只有跟 MySQL 当前版本一致的 Segment 才继续往下走。

这个分工也决定了出故障时信谁。Elasticsearch 里多出一个未激活的版本，不改变用户看到的文档。清理任务短暂失败，当前生效的内容也不会突然不可用。它做不到像数据库事务那样两边同时成功或同时回滚，但用户什么时候看到新版本，只由 MySQL 里那次版本切换决定。

版本可见性定下来，当前查询能用哪些内容也就清楚了。接下来的问题落在检索本身。同一个问题，既要找到准确的原词，也要覆盖意思相同的不同说法。

一次搜索，要同时照顾“原词”和“大意”

召回之前，系统得先确定这次搜索能落在哪些文档上。用户是在整个知识库里问，还是只在一份技术手册里查，这个范围必须先圈好。查询改写可以改“拿什么话去搜”，不能顺手把范围放大，否则不在当前上下文里的资料也会混进答案。

范围定了，才轮到处理用户这句话本身。比如用户先问“PostgreSQL 的 Serializable 隔离级别为什么还会让事务失败”，接着只问一句“只读事务也会吗？”。直接拿后一句去搜，数据库、隔离级别、序列化冲突这些前提全丢了。Anchr 会结合最近几轮对话改写查询。改写模型超时，或者输出不合法，就退回原问题继续搜。改写只是帮召回，不能顶替用户问的那句话。

改写后的查询进多路召回，就是同时用几种办法找候选。全文检索擅长命中类名、错误码、配置项和文件标题这些明确的词，向量检索负责覆盖不同说法。用户问“为什么数据库为了保证可串行化反而会主动回滚事务”，文档里写的可能是“检测到可能产生不可串行化结果的读写依赖，需要中止其中一个事务”。话说得不一样，说的是同一件并发控制的事。

反过来，SQLSTATE 40001、could not serialize access due to read/write dependencies among transactions 这种标识和原始报错，一旦被泛化成语义，精确度反而掉下来。所以全文检索没法被向量检索替掉。Embedding 支持图片时，同一个查询向量还能去匹配依赖关系图和技术手册里抽出来的图。

三路召回的原始分数不在一个尺度上。直接相加，分数量级大的那一路就占便宜。Anchr 用 RRF 合并，它不比原始分数，看的是候选在各路结果里排第几，按名次累计贡献。同一个 Segment 既命中配置项原词，又跟问题语义接近，就有两路支持。只在某一路出现的内容，也不会因为分数不可比就直接消失。

融合完先过一遍当前索引版本，再整理结果交给 Rerank。重排模型会细一点地判断候选跟问题到底相关多少。顺序很要紧。旧版本的片段再相关，也不该占着后面的候选名额，更不值得花掉一次重排。版本过滤放到最后，过期内容还可能先一步挤掉本该进重排的新版片段。

一份长文档里相邻的几段经常同时命中。不处理的话，前十条里大半来自同一份文件。搜整个知识库时，Anchr 会限制同一文档、同一类型的候选数量，给别的资料留位置。这不代表别的文档更正确，只是别让一份长文档靠片段数量占满那几个位置。已经限定在单份文档里搜的时候，目标变成找这份文档里最相关的位置，打散就挪到 Rerank 之后，免得提前删掉有用的连续片段。

Rerank 只处理已经收窄的候选，它没有第二次召回的机会。被搜索范围、版本或者数量限制挡在前面的内容，它找不回来。最终顺序会同时参考调到同一尺度后的检索得分和 Rerank 得分。Rerank 服务失败或者返回空结果，就保留 RRF 的原顺序。这条降级路能保住已经拿到的结果，救不回召回阶段就丢掉的东西。

排完序的候选还在手里。它们适合人看，不适合原样塞给模型。

搜到的结果，还不能直接交给模型

搜索页面和问答模型要的东西不一样。人可以扫几张卡片，挑一条点开继续判断。模型的上下文有限，每放一个片段都在吃窗口，引用和结论对不上的机会也一起变多。

Anchr 先把排好的 Segment 按文档合成结果卡片，每份文档只留排名靠前的几个命中位置。用户看到的是“哪些资料值得打开”，不是十几条同一份文件里的碎片。这些结果更像阅读导航，不用和最终答案用的证据完全一致。

固定 RAG 会从这些结果里再挑一次，最多选 5 个能追溯、能引用的片段。条件是它得有真实的 Segment 标识，对得上页面展示的结果，也有能拿去回答的文本证据。数量卡死，模型就只能在这几段里组织答案。搜索返回的前 K 个全塞进 Prompt，重复片段、弱相关段落、互相打架的版本说明会一起进去，模型得先替检索系统做一遍去噪。

图片召回还有个边界。纯视觉向量能帮着找到一张相关架构图，可当前没有能引用的文本，它就不会直接变成知识型回答的根据。帮得上排序，不等于已经是可以表达、可以核对的证据。

进生成阶段的 Prompt 不光是问题加几段文本。里面有用户的原始问题、检索时用的改写查询、当前回答模式，还有一份编过号的证据列表。原问题保住用户的真实意图，改写查询说明这次实际拿什么话去搜的，证据列表划定模型能用的事实范围。分开写有个用处。为了搜得更全而补出来的那句查询，不会在生成阶段反过头改掉用户原本的问题。

调用回答模型之前，后端先做一次证据检查。没有可引用的 Segment，有效内容太短，或者检索分数低、证据又少，系统直接返回证据不足，不让模型在薄薄一层上下文上把答案补齐。这样一来，“没找到足够证据”和“模型调用失败”成了两种不同的结果。

过了这道检查，模型才开始写。写完也不等于能直接交给用户，后端还要看它有没有守住证据规则。

模型写完了，后端还要验收

回答模型要返回带状态和引用编号的结构化结果。有证据是 ANSWERED，证据不足是 NO_EVIDENCE。NO_EVIDENCE 说明检索和生成都正常跑完了，只是现有资料撑不住结论。模型超时、协议解析不了、调用抛异常，那是生成失败。这两种分开以后，用户才知道该换个问法、补点资料，还是过会儿再试。

就算模型返回 ANSWERED，这份回答也只是候选。它可能输出不合法的 JSON，引用一个根本不存在的编号，或者给出知识型结论却一个引用都没有。这些问题靠 Prompt 里一句“请勿编造”解决不了，后端拿代码里的固定规则去查。

Anchr 会解析模型返回的结构，看回答状态、引用编号有没有超出输入的证据、知识型回答是不是真的用上了引用。模型只拿到 1 到 5 号证据，回答里冒出个 [7]，这份回答就过不去。

验收通过以后，后端只留答案实际引用的 Segment，不会把候选全包装成“参考资料”。这些 Segment 再按文档合并、重新编号，补上文件、页码、原文位置和命中原因。模型没写合适的引用说明，系统就用检索阶段已经生成的匹配摘要顶上，省得为了装饰引用再补一条理由。前面解析阶段留下的位置信息，到这一步才变成能点回去的路径。

回答和搜索结果卡片是两样东西。模型可能只用了两个 Segment，页面上照样保留其他高相关结果，用户可以接着读。证据没到回答的门槛，系统也可以留下已经找到的文档线索，同时讲清楚暂时给不出有证据的结论。没生成答案，不代表这次搜索白搜。

回答一点点往外显示的时候，模型回给后端的状态、引用编号这些协议字段不会露在页面上。服务端从增量输出里只取能看的正文。完整结果验证完，最终文本跟前面的临时内容对不上，页面再用验证过的版本校准。边生成边显示是为了少等一会儿，最后那次校验才决定这轮回答成不成立。

引用、回答状态、结果卡片，还有这次查询走过了哪几步，都会跟着本轮会话存下来。刷新页面，结果还在。留下这条检索轨迹，回答不理想时能往前查。是查询改写偏了，是召回没找到，还是被版本过滤、重排、证据检查或者生成校验挡住的。只留一段回答，这条流程就又成了黑盒。

引用说明的是“这段回答用了哪份资料”，管不了模型对资料的理解对不对。PostgreSQL 文档写的是“VACUUM 不能清理仍可能被活动事务快照看到的旧行版本”，模型照样可能概括成“长事务会阻塞 VACUUM”，把“部分旧版本回收不了”放大成“整个清理都跑不动”。引用修不了这个结论，但它至少让人能直接翻开原文看一眼。到这一步，固定 RAG 的流程才算走完。

固定 RAG 现在做到了哪里

现在的 Anchr 能把原始资源转成可搜索、可回溯的证据，全文、文本向量和文档图片一起参与召回，筛过的证据再交给回答模型。回答过了引用校验，会跟搜索结果一起存下，用户还能回原文接着读。

没补齐的地方也有。入库任务在主服务重启后还不能从中间某个阶段原地续跑。搜索这边有多路召回、RRF 和 Rerank，但没有大规模人工标注的数据撑着，离线评测做不完整。接下来要补的是搜索评测、入库中断后的恢复路径，还有把回答失败和证据不足分得更清楚。

这些都在固定流程里面。另有一类问题，把一次检索调得再准也解不了。

一次检索不够，才需要 Agent

这篇文章里的 RAG 在生成之前只检索一次。问“PostgreSQL 的普通 VACUUM 为什么通常不会缩小表文件”，一次检索要是已经把空间复用和文件回收的区别找齐了，固定流程就够用。

换个问题，“PostgreSQL 只读副本的延迟为什么持续上升”。它牵到 WAL 的发送、接收和回放位置，可能还要核对网络吞吐、回放冲突、长查询和当前部署参数。第一次搜索先把延迟卡在哪一段找出来，才知道下一步是查传输链路还是查回放过程。后面的搜索方向取决于前一步读到的东西，固定 RAG 在这里就走到头了。

Anchr 的 Agent 从这个边界开始。它没有另起一套知识流程，沿用的是前面那套检索、版本过滤和引用规则，只是让模型可以根据中间结果继续搜、继续读。这个循环为什么需要预算、状态和证据边界，我放在下一篇《一次 RAG 不够怎么办》里讲，那篇写的是 Anchr 迭代 Agent RAG 的全过程。
