会话应该是实现细节

发表于 2026-11-03 分类于 AI 工程化

10 月 31 号晚上，DeepSeek Harness 团队发了篇长文：《Super-agent 设计探索：迈向更自主的 Agent 系统》。

整篇读下来，最戳我的是这句话：Session 应当是系统的实现细节，而不应是用户的认知负担。

文里提到，一个人通常只能同时盯住 3 到 5 个活跃会话。我对照自己日常的状态数了一下，确实差不多——到了第六个窗口，脑子里就会开始出现“我记得有个任务在等 CI，但死活想不起来切去哪个标签页找”的状况。

他们把这叫“瓶颈转移”：单任务的上限取决于模型能力，多任务的上限取决于人的注意力。前半句现在基本是行业共识了，而后半句，正是这套系统想解的题。

倒不是为了省 token。主要是之前那套 orchestrator 加三个 subagent 的结构太折腾人：每加一个功能，我得同时改四个地方——路由的分类规则、subagent 自己的 prompt、主 agent 的 prompt，还有交接时的字段约定。

一次 RAG 不够怎么办：Anchr 迭代 Agent RAG 的过程

发表于 2026-08-11 分类于 AI 工程化

Anchr 最开始只有一条传统的 RAG 链路：用户提问，系统搜出相关内容并重新排序，挑前几个片段塞给模型，最后生成带引用的回答。

应付大多数事实型问题，这条链路足够了。比如问“文档重新解析后，旧索引怎么处理”，只要知识库里有说明，搜一次基本就能拿到核心材料，剩下的就是让模型整理成通顺的话。

但有些问题没法这么干：

找出几份设计文档里所有与任务恢复有关的内容，再比较进程重启、网络断开和主动取消三种情况下分别会发生什么。

这种问题很难靠现成的几个片段拼出答案。第一次搜索可能只翻出 Agent 运行恢复的说明；顺着读下去，才发现还牵扯到异步任务（Task）；掉头去查 Task，又冒出进程内状态和持久化状态的区别。等最后去核对部署约束时，你对“恢复”这两个字的理解，早就和第一轮搜索时不一样了。

下一步搜什么，完全取决于上一步读到了什么。Anchr 的 Agent RAG 就是为了解决这种问题做出来的。

我做了一个文档知识工作台：从搜索到 RAG，再到 Agent

发表于 2026-08-11 分类于 AI 工程化

最开始做 Anchr，我想解决的问题很具体：手里的文档越攒越多，怎么才能把里面的信息重新捞出来、真正用起来？

文件夹目录只能解决“文件存在哪”，系统自带的全文搜索又要求我必须记得原文用过哪些词。资料少的时候还能凑合；资料一多，常态就变成了：我明明记得某份文档聊过这事，但早忘了文件名，也想不起当时具体是怎么表述的。

所以 Anchr 是从文档搜索切入的。等搜索基本能用了，我才在检索结果之上接了生成回答；再往后，发现单次检索根本应付不了跨文档的复杂排查，这才顺理成章长出了 Agent。

虽然功能模块的名字一路从 Search 变成 RAG、再变成 Agent，但底下干的始终是同一件苦力活：把原始文档稳定地拆解成模型能用、用户又能随时跳回原文核对的证据。

INTJ：礼貌、疏离，自我闭环

发表于 2026-02-11 分类于 个人思考

刚认识 INTJ 时，多数人会觉得他们挺好相处。

说话留余地，做事有章法，遇到突发状况也很少慌乱。分内的事不推诿，不懂的领域不乱接话，不管对方是什么头衔，态度都差不太多。虽然算不上热情，但让人觉得踏实、好沟通。

可处久了，不少人会撞上一堵无形的墙：客气还是那么客气，距离却一点没近。

你们可以聊工作、拆解具体问题，他甚至会给你非常诚恳的建议，但你很难真正走近他的私人生活。这种疏离不是因为闹了别扭，也不是对你有意见，他只是从来不觉得“认识久了，关系就该自动升级”。

摸清 INTJ，大概要先从这一点开始：礼貌是他给所有人的体面，亲近则是另一套严苛的筛选。

我给图片搜索加了向量，然后发现还不够

发表于 2025-06-14 分类于 AI 工程化

如果只记得一张图的大致内容，却忘了文件名，怎么把它找出来？我做 PicIndex，最初就是为了解决这个问题。

思路其实不复杂：用多模态 Embedding 把图片和文字映射到同一个向量空间。这样搜“赛博朋克风格的雨夜街道”或者“坐在窗边的猫”，系统就能顺着画面语义找出相似的图。

Demo 跑通得很快，但真当成工具用起来，毛病就全冒出来了：图里的订单号搜不准、几兆的原图调一次模型慢得离谱、同一个热词每次搜都要重新算一遍向量。

折腾了一圈之后我发现，这些问题最后都没靠“换个更强的模型”来解决。PicIndex 后来真正管用的改动，几乎全发生在模型之外的工程链路里。
