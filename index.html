把 subagent 放回主循环

发表于 2026-11-01 分类于 AI 工程化

上个月我把手上一个 agent 应用里的三个 specialist 删了。

不是为了省 token，而是那套 orchestrator 加三个 subagent 的结构，每加一个功能我要改四个地方：路由的分类规则、subagent 自己的 prompt、主 agent 的 prompt，还有交接时那份字段约定。改完还得赌两边对“用户到底想要什么”的理解是一致的。

删完跑我们那套没几个 case 的回归，任务完成率没掉，端到端延迟掉了将近一半。这个数字是拍脑袋得来的，并没有做 A/B，后面会提到别人认真的测量，结论差不多。

Anthropic 的 Applied AI 团队在 10 月 22 号发了一篇文章，Building agents: When to fold subagents into your main agent loop。我第一反应不是“又多一个方法论”，而是“原来不只是我们这么干，而且他们把原因写清楚了”。

一次 RAG 不够怎么办：Anchr 迭代 Agent RAG 的过程

发表于 2026-08-11 分类于 AI 工程化

Anchr 最早只有一条普通的 RAG 链路。用户提问，系统检索，重排候选，把排在前面的几个片段放进上下文，模型据此写出带引用的答案。

事实型问题走这条链路还行。比如问“文档重新解析后，旧索引怎么处理”，知识库里只要有对应说明，一次检索就能把材料捞上来，剩下的活是把它整理顺。

另一些问题的形状不一样。

找出几份设计文档里所有与任务恢复有关的内容，再比较进程重启、网络断开和主动取消三种情况下分别会发生什么。

这种问题很少有哪个现成片段能答完。第一轮搜索多半只找到 Agent 运行恢复的说明，读下去才知道后面还牵着异步任务（Task）。再去查 Task，又撞上进程内状态和持久化状态的区别。等翻到部署约束那一节，“恢复”这两个字的意思已经和第一次检索时不一样了。

下一步搜什么，得看上一段读到了什么。Anchr 的 Agent RAG 就是从这类问题上长出来的。

我做了一个文档知识工作台：从搜索到 RAG，再到 Agent

发表于 2026-08-11 分类于 AI 工程化

最开始做 Anchr，我想解决的问题很具体。手里的文档越来越多，怎么才能把里面的信息重新找出来、用起来？

目录解决的是文件放在哪里。系统自带的全文搜索要求我还记得原文用过哪些词。资料少的时候，这两种办法都够用。资料一多，更常见的情况是我记得某份文档讲过这件事，却忘了文件名，也不记得当时那句话是怎么说的。

Anchr 就从文档搜索做起。搜索能用了，我才在检索结果上生成回答。再往后，一次检索处理不了跨文档的问题，才有了 Agent。功能名字从 Search 换成 RAG，又换成 Agent，底下做的还是同一件事，让原始资源稳定地变成模型可以用、用户又能回到原文核对的证据。

如果只记得一张图的内容，却忘了文件名，怎么把它找出来？PicIndex 就是为了回答这个问题。

我用多模态 Embedding 把图片和文字映射到同一个向量空间。搜“赛博朋克风格的雨夜街道”，或者“一只坐在窗边的猫”，系统会按画面语义把相近的图找出来。功能跑起来以后，问题一件接一件。图片里的订单号搜不准，大图调模型太慢，同一个查询还要一遍遍重新算向量。

长期焦虑之后，人为什么容易走向虚无或者及时享乐？

发表于 2024-04-07 分类于 个人思考

这几年我见过一种变化。有人一直在努力，日子却越过越紧，慢慢地，他说不清自己图什么。也有人原本对以后有安排，熬了几年，只想说一句算了。

这两种反应看着方向相反。一种把意义整个放下，努力有什么用，成功又有什么用。另一种掉头去抓眼前，吃顿好的，买点喜欢的，打几把游戏，看电影，出门一趟。远处的目标忽然比不过今天下午的快乐。

我把它们放在一起看，是因为它们常常出现在同一个人身上，隔一段时间换一种。共同的地方大概在这里，他不太相信自己的动作还能改变后面的事。

下面说的虚无，指日常里那种提不起劲的感觉，跟哲学课上讨论的虚无主义不是一回事。我关心的问题小一些，一个人怎样从“我还想改一改将来”，走到“做什么都没用”，或者“至少先抓住眼前”。

这些事我原先只有模糊的印象。后来把能找到的实验、队列研究和汇总分析翻了一遍，才对上其中一部分。下面写到的地方，能查出处的都标了来源，查不到的我就不写。
